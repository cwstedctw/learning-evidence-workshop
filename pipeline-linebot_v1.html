壹這份作業要交什麼、怎麼評

作業例子：第 5 週：LINE Bot 第一版，五件事：專題計畫六項、GitHub 專案、AI 做的開發紀錄網頁、簡報、實測證明與如實進度。 和AI一起寫程式課程網 ↗

評分方式：三個 AI 評分者各打一份（linebot_v1 草稿）→ 平均後對齊到 80–100 分

怎麼檢查（不只比對文字）：五件事各自檢查：GitHub 連結打得開而且看得到這個 Bot 的程式、開發紀錄網頁打得開、簡報 4 頁以上、測試紀錄至少三項（測什麼、預期、實際）＋看得見的實測證明（截圖、影片或輸出）；如實寫出哪裡還沒做好本身就是得分點。

評分表備註（工作紀錄原文，含內部用語）

2026-10-09 洄瀾依 27 份實際繳交擬（草擬後由老師確認）。五維對應作業說明的五件事：專題計畫（附件六項）、GitHub 專案、開發紀錄網頁、簡報、實測證明與如實進度。設計要點：①「如實寫出目前進度、測試結果、待改善問題」本身就是得分點，所以 evidence 配最重（35），而且「還沒實測但寫出卡在哪＋下一步」有 20；②格式不拘：PDF、PPTX、HTML、Markdown、DOCX 都算，計畫寫在計畫檔、簡報或網頁裡都算；③不苛求美觀、功能多寡、有沒有串生成式 AI；本機測試（不經 LINE）算實測；④AI 產出的企劃書照六項逐項看，篇幅長、用詞華麗不加分，無根據的效益數字不扣分；⑤連結是活的、很多人課後已改成改善版，評分看交件內容，連結現況只確認打得開、是不是這個專題、有沒有實測段落。評分者依本表打 原始分，取平均後照 對齊；原始分低於 40 落 60–79。

評分表怎麼來的：評分表不是先寫好再收作業：先把全班的繳交一鍵抓回來，AI 讀完全部材料、列出看得見的維度與配分，老師確認後才開批。沿用同一份評分表的作業不必再確認。

貳評分表：5 格、共 100 分

維度配分怎麼給分
專題計畫六項20六項＝①專題名稱 ②使用對象與用途（誰用、解決什麼問題）③核心功能（具體一項以上）④對話範例兩組：正常使用＋一種異常情況（輸入不完整、不支援或無法回答，任一種都算）⑤AI 協助方式（打算請 AI 做哪些事）⑥測試計畫：三個情境以上且寫出預期結果（寫成測試結果表也算）。計畫寫在計畫檔、簡報或線上文字指到的網頁／README 裡都算。20＝六項都有。14＝有四到五項（常見缺：④沒有異常情況的例子、⑤沒寫 AI 協助、⑥不到三個情境或沒預期）。8＝只有兩到三項；或是 AI 產出的技術企劃書／實作計畫，看得到名稱與功能，但對話範例、測試計畫、使用對象大多沒有。3＝只有題目或一兩句；只有 AI 對話截圖裡的計畫開頭；或只在 repo 裡找得到計畫檔（見 ）。0＝沒有計畫；上傳的是作業說明原檔、沒有填任何內容也算 0（但簡報或網頁裡有計畫內容的照上面評）。
GitHub 專案1515＝線上文字或上傳檔裡有 GitHub 專案連結、打得開，裡面看得到這個專題的 Bot 程式。連結貼成 repo 裡的單一檔案、commit 頁、加 .git 結尾、或沿用之前練習用的 repo 都不扣。8＝打得開，但只有說明文件或單一範例，看不出能執行的 Bot 程式。3＝打得開但是空的，或內容跟這個 LINE Bot 專題無關（可能貼錯，列 ）。0＝沒有 GitHub 連結，或打不開。README 寫得多完整、commit 幾次，第一版都不計分（那是改善版的要求）。
開發紀錄網頁1515＝線上文字貼了開發紀錄網頁連結、打得開，是這個專題的紀錄（看得到專題介紹、開發過程或測試段落任一塊）。版面簡單、內容少都不扣；網頁現在已改成改善版、第一版另存在別頁也不扣。10＝做了但不完全：把 GitHub README 連結當網頁貼；用 AI 做了 HTML 開發紀錄檔，但沒發布成網址（改上傳或放在 repo）；或網頁已發布、repo 裡看得到，但線上文字沒貼連結。5＝網頁欄貼的東西不是開發紀錄（例：程式檔、Bot 伺服器的健康檢查頁、跟紀錄無關的測試頁）。0＝沒有。「線上文字寫出實測證明在哪一段」寫了更好，沒寫不另扣（實測本身在 evidence 評）。
簡報1515＝有這個專題的簡報 4 頁以上（PDF、PPTX、HTML 投影片都算；空白頁不算頁數），內容講專題本身（介紹、功能、架構、進度或測試任一塊）。8＝簡報只有 1–3 頁；或沒有投影片形式的簡報，但交了一份含成果／進度的多頁文件（成果報告、附驗收結果的企劃書）當作簡報。3＝沒上傳，但 repo 裡有交件當天 commit 的簡報檔（見 ）。0＝沒有簡報；只交計畫檔、README 列印、通用教學指南或截圖都算沒有。同一份文件若同時有計畫與成果，可以同時算 plan 與 slides。
實測證明與如實進度35三要素：(a)測試紀錄——至少三項測試，每項寫出測什麼（傳了什麼訊息或做了什麼操作）、預期（或判準）、實際結果；測 Bot 功能或串接環節（Webhook 驗證、健康檢查、API 連線）都算；(b)看得到的實測證明——截圖、影片、測試執行輸出（終端機、pytest 結果文字）、部署 log，放在網頁、簡報、上傳圖檔都算；只有「✅ 過關」這種文字摘要不算證明；(c)寫了目前進度或待改善問題（下一步、未完成的功能、已知限制都算）。35＝三要素都有。如實寫「LINE 真機還沒測、只做本機測試」不扣分。28＝三要素缺一（常見：測試結果只有文字「過關」沒有證明；有真機截圖但沒有輸入／預期／實際的測試紀錄）。20＝有實際跑過的具體痕跡但不完整：一張實測截圖，或一句寫出實際結果的描述（傳了什麼、Bot 回了什麼、回答品質如何）；或還沒實測，但如實寫出卡在哪＋測試計畫或具體下一步。10＝只有籠統的進度狀態（「已完成✅」「測試過關」）；只有測試計畫（預期）沒有實際結果；只有一句「暫無／之後補」或只寫原因沒寫下一步；或測試與進度內容只在 repo 裡、線上文字與上傳檔都沒指到。0＝完全沒有實測、進度或問題說明。

肆3 個評分者差多少、差在哪一格

這種作業一共 27 份作答，每份有 3 個評分者的分數（立霧（Codex）、洄瀾（Claude）、秀姑巒（Gemini））。最高減最低的差距 15 分以上的有 7 份（26%）——這些由老師親自看。

最常分歧的一格是「實測證明與如實進度」（評分者兩兩相減平均差 3.0 分）。分歧集中在哪一格，多半是那一格還不夠「看得見」（也可能是抽字或照片辨識的問題），回查原件再決定下一版怎麼改。

到 2026-10-09 為止，老師最終分數那一欄還是空的：目前用對齊分推簿，分歧大的個案在關注名單上另外看。
